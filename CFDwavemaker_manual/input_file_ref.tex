\section{Input file reference}

The input file is organized in \textbf{[sections]} of \texttt{keyword value} lines. The reader is robust with respect to layout: the sections may appear in \emph{any order}, and within a section the keyword order is also free (component tables must remain contiguous blocks, with frequency rows before directional rows). Anything after a \texttt{\#} is a comment and blank lines are ignored. Unknown section names and unknown keywords produce a warning (so typos are not silently ignored), a malformed number is a hard error, and a duplicated section is a hard error.

\subsection{[wave type]}
CFDwavemaker currently support the following wave theories. Which branch of wave theory to used is controlled by the keyword \textbf{[wave type]}
\begin{enumerate}
    \item \textbf{irregular} - irregular wave theory (linear or second order)
    \item \textbf{regular} - Stokes regular wave theory (up to 5th order)
    \item \textbf{piston} - Wave maker theory
    \item \textbf{swd} -  Spectral-Wave-Data file (swd)
    \item \textbf{vtk} - VTK library is another external library which is supported by most CFD programs. By building and linking this with CFDwavemaker, kinematics can be imported from any program capable of writing vtk files.
    \item \textbf{slope} - Initialise with water at rest with a given slope
\end{enumerate}

To chose one of the above use the following code word
\begin{lstlisting}[]
[wave type]
# This is a comment
irregular
\end{lstlisting}
where any lines starting with \# are regarded as comments in the input file and will be ignored during execution.

\subsection{[wave input regular]}
This section defines a single regular (periodic, permanent-form) wave. Two wave theories are available, selected with the \texttt{theory\_type} keyword:
\begin{itemize}
    \item \textbf{stokes} (default) --- 5th-order Stokes theory. Sir George Stokes solved this nonlinear wave problem in 1847 by expanding the relevant potential flow quantities in a Taylor series around the mean (or still) surface elevation. As a result, the boundary conditions can be expressed in terms of quantities at the mean (or still) surface elevation. Stokes' regular wave theory is of direct practical use for regular waves in intermediate and deep water. The implementation in CFDwavemaker is based on Fenton (1985) and goes up to 5th order.
    \item \textbf{stream} --- Fenton stream-function theory. Instead of a fixed-order perturbation expansion, the Fourier coefficients of the stream function are found numerically by solving the fully nonlinear steady-wave boundary-value problem (Fenton, 1988; Rienecker \& Fenton, 1981). This is accurate for steep and/or shallow-water waves where the Stokes expansion loses accuracy, up to close to the breaking limit. The number of Fourier modes is set by \texttt{wave\_order}.
\end{itemize}
Both theories share the same wave-property keywords (\texttt{wave\_length}/\texttt{wave\_period}, \texttt{wave\_height}, \texttt{current\_speed}); if \texttt{theory\_type} is omitted the Stokes theory is used, so existing input files remain valid.

\subsection{[wave input swd]}

This provides a very useful extension to CFDwavemaker, which facilitates external wave theories, as long as they can write the output in the SWD format. \subsection{[wave input vtk]}
The VTK library (Visialization Toolkit) is open source and widely used in the CFD industry. It supports a wide range of formats, covering pretty much all thinkable grid types used by CFD solvers. Compiling CFDwavemaker with this extension library therefore expands its usage and enables CFDwavemaker to read kinematics from most wave models, as long as they can export their result into one of the hundreds of formats that VTK supports.

However, the many formats supported in the VTK library have different functions for loading and extracting data. Hence, supporting them all implies a lot of coding. For now, the structuredXMLGrid format (.vts) is supported, which is an ideal format for storing Eulerian and Lagrangian mesh data on a cartisian grid. More formats, like the octree-format (.htg) or the versatile UnstructuredXML format (.vtu), will surely be implemented in the future as the need arises.

\textbf{NOTE:} The .vts format was implemented to specifically read kinematics from a multilayer solver, on a vertical lagrangian grid. This means that the free surface is given by the grid itself and not a volume fraction (as the example given in Fig. 4.2). Reading multiphase data separated by volume fraction field data is surely something that will be added but not done yet.

\textbf{Multilayer fields (\texttt{h} and \texttt{phi}).} When the .vts files come from a multilayer solver they may additionally carry two cell-centred fields, which CFDwavemaker detects automatically (checked once, on the first file loaded):
\begin{itemize}
    \item \texttt{h} --- the layer thickness of each cell. When present, the free-surface elevation $\eta$ is computed as the exact per-column sum of the layer thicknesses (more accurate than reading the top grid point), and the velocity is reconstructed directly from the cell centres --- using the scheme selected by \texttt{vertical\_interp} --- rather than by averaging the cell data onto the grid nodes.
    \item \texttt{phi} --- the non-hydrostatic pressure. It is stored at the cell centres but is defined on the \emph{lower} interface of each layer, so the value in the lowest cell is the seabed value and the value at the free surface is zero by definition. It is reconstructed on the layer interfaces and returned through \texttt{wave\_nhPres()}.
\end{itemize}
If neither field is present the reader falls back to its original behaviour, so older files remain valid.

\textbf{2D data used in a 3D domain.} A 2D (long-crested) simulation is written in the $x$--$y$ plane with $y$ as the \emph{vertical} axis, whereas a 3D CFD domain uses $z$ as the vertical axis. CFDwavemaker reconciles the two automatically: if the .vts grid is 2D (a single cell in the third index) the kinematics are interpolated in the $x$--$y$ plane, the requested \texttt{z} coordinate is used as the vertical position (mapped onto the vts $y$-axis), and the requested \texttt{y} coordinate is ignored. The velocity components are mapped to match, so that
\begin{center}
\texttt{wave\_VeloX}$=u$ (horizontal),\quad \texttt{wave\_VeloZ}$=w$ (vertical),\quad \texttt{wave\_VeloY}$=0$.
\end{center}
For genuinely 3D .vts data the natural mapping is used. In short, within CFDwavemaker \texttt{z} is always the vertical axis, whether the source data is 2D or 3D.

An example of reading kinematics input from .vts files are given below
\begin{lstlisting}[]
@v301
# wave kinematics read from vtk files
[wave type]
vtk

[wave input vtk]
storage_path ../subdomain/
filename subdomain
name_velocity_field Velocity
\end{lstlisting}

\subsection{[seabed]}
Optional section for specifying \textbf{variable bathymetry} from a triangulated surface file. When present, the irregular-wave kinematics switch to a slope-corrected first-order evaluation: at every point the local depth $h(x,y)$ and bed slope $\nabla h$ are probed from the surface, each component's wavenumber is re-solved from the local dispersion relation $\omega^2 = gk\tanh(kh)$, and the Airy vertical eigenfunction is replaced by
\[
F_j(z) = \frac{\cosh k_j(z+h) - i\beta_j \sinh k_j(z+h)}{\cosh k_jh - i\beta_j \sinh k_jh},
\qquad \beta_j = \hat{\mathbf{k}}_j\cdot\nabla h ,
\]
which satisfies the sloping-bottom kinematic condition $w + \nabla h\cdot\mathbf{u}_H = 0$ at $z=-h$ exactly. Each directional component receives its own correction $\beta_j$, so oblique and short-crested seas are handled consistently. The first-order surface elevation follows from the dynamic surface condition of the same potential: since $F_j(0)=1$ identically, it is the plain component sum with the \emph{local} wavenumbers in the phase --- surface and kinematics therefore share one phase function and stay aligned across the slope.

The seabed surface is given as a geometric surface $z_{\mathrm{bed}}(x,y)$ ($z$ up, still water level at $z=0$ unless shifted with \texttt{zshift}); the water depth is $h = -(z_{\mathrm{bed}} + \texttt{zshift})$. Supported formats (selected by file extension) are STL (ascii or binary, auto-detected) and Wavefront OBJ --- both easily exported from Paraview, Blender or any CAD tool. Queries outside the triangulated footprint clamp to the nearest mesh point (constant depth, zero slope), so a bathymetry patch smaller than the CFD domain degrades gracefully.

Since potential wave theory is invalid (and numerically explosive) as $h\rightarrow 0$, a minimum-depth limit is enforced: where the surface is shallower than \texttt{min\_depth}, the depth is clamped to that value with zero slope (a flat shelf). Set it from the sea state --- waves break around $h \approx 1.3 H_s$.

When a \texttt{[seabed]} section is present, the \texttt{depth} keyword under \texttt{[general input data]} must \emph{not} be given (the water depth is defined by the seabed surface everywhere; an error is raised otherwise). \texttt{[seabed]} may be combined with \texttt{[lsgrid]}: the grid layers then follow the local depth (per-column sigma mapping) and the grid is filled from the slope-corrected kinematics. The sigma-FFT fast path and the periodic domain lock are disabled with variable bathymetry (they assume uniform depth and spatial periodicity); the grid is filled pointwise.

The second-order contribution is retained with variable bathymetry: the Sharma--Dean interaction coefficients are evaluated at the \emph{local} depth $h(x,y)$ with local wavenumbers (the slope correction itself is applied at first order only, where most of the wave energy resides). The interaction limit on sum interactions ($k_i + k_m \le k_{\max}$, required for wide-banded spectra with fat spectral tails) is applied to \emph{cross} interactions; the \emph{diagonal} self-interaction (each component's own Stokes second harmonic, which is bounded and physical) is kept in both the elevation and the kinematics so the exported surface and the kinematics are mutually consistent. Note that \texttt{[seabed]} is supported for irregular waves only (direct evaluation or lsgrid).

Independent of \texttt{[seabed]}: the wavenumber column of the component table is always recomputed from $\omega$ through the dispersion relation at the reference depth (the column is overspecified); a warning is issued if the file values disagree by more than 0.1\,\%, which usually means the file was generated for a different water depth.

\subsection{[lsgrid]}
The lsgrid may be combined with two kinematics sources: \textbf{[wave type] irregular} (second-order irregular wave theory) and \textbf{[wave type] swd} (Spectral-Wave-Data files).

\textbf{Equal-dk lattices (sigma-FFT fill):} when the components form an
equal-dk lattice (\texttt{equal\_dk 1} + \texttt{vertical\_theory smit},
no seabed), the grid is filled with per-layer FFTs and the lsgrid is
\emph{snapped to the FFT nodes} at load time: the FFT evaluates one full
spatial period $L_x = 2\pi/\Delta k_x$ (and $L_y$ for 2D lattices)
anchored at the grid origin, but only the nodes inside the requested
bounds are stored. The grid spacing is pinned to the node spacing
$L/n_\mathrm{fft}$ (every stored value is an exact collocation value of
the second-order solution), \texttt{xmin}/\texttt{ymin} are kept as
given, and \texttt{xmax}/\texttt{ymax} round outward to the next node.
Size the bounds to the CFD domain (plus ghost-cell margin) --- storing
the full period is unnecessary and can cost an order of magnitude more
memory; the border selection composes with the window for
boundary-only updates at $t > 0$. The file's \texttt{nx}/\texttt{ny} act
as a lower bound on the per-period FFT resolution (the actual values are
reported at startup). Bounds covering a full period lock to exactly one
tile and the field is treated as periodic in that direction. With SWD, the wave field --- possibly of higher order, e.g.\ from a HOSM simulation --- is pregenerated once into a \texttt{.swd} file and then sampled onto the grid; all CFD-side queries are subsequently served by thread-safe spline interpolation, which avoids the serialization otherwise required when querying the (stateful) swd library directly from a multithreaded solver. Note that the swd sampling itself runs serially within each process (the swd library supports a single reader object per process); under MPI, each rank samples its own column block of the grid.

\textbf{How much of the grid is actually stored (v3.7.5).}
The lsgrid field arrays used to be allocated for the full \texttt{nx\,$\times$\,ny\,$\times$\,nl}
box regardless of which region was in use; the excluded region only skipped
\emph{computation}, never storage. A run feeding waves in through its boundaries
therefore paid for the whole domain, on every MPI rank. The storage is now
compacted to the region that is actually queried, which for a typical
boundary-fed case is a few per cent of the box (a $257\times257\times10$ grid
feeding one border drops from roughly 230\,MB to under 10\,MB per rank).

Kept is the requested region plus a three-node halo. One ring is needed because
the bilinear/tricubic gather reads the far corner of the interpolation cell, a
second because those corner nodes must carry valid finite-difference gradients,
and a third as margin so the gradient-valid region reaches two full nodes past
the requested region rather than ending exactly on its edge. Requesting
kinematics at a point that was dropped is a hard error naming the point and how
far inside the ignored region it lies --- previously such a query silently
returned uninitialised memory.

\textbf{Setting the grid from the CFD code.} The extent and the active borders
can be set programmatically instead of in \textit{waveinput.dat}, which avoids
duplicating the domain bounds in two places where they can drift apart:
\begin{lstlisting}[language=C]
int wave_SetLsgridBounds (double xmin, double xmax, double ymin, double ymax);
int wave_SetLsgridBorders(int left, int right, int bottom, int top);
int wave_SetBorderMargin (double metres);
\end{lstlisting}
\texttt{wave\_SetBorderMargin()} states how far \emph{inward} from a border the
caller will request kinematics. Without it the stored strip is sized in grid
nodes, which stops being sufficient once the caller's own cells are coarse
relative to the node spacing --- a coarse CFD grid over a finely resolved wave
lattice. Given it, the strip is sized in metres and the mismatch cannot occur.
For a boundary-fed solver the reach is typically half a CFD cell.

All three must be called \emph{before} \texttt{wave\_Initialize()} --- the grid is
built during initialization --- and both return 0 without doing anything if
called later. Values given this way override the corresponding keywords in the
input file.

\textbf{Additional notes on LSgrid:}
\begin{itemize}
    \item For long crested simulations it is sufficient to have a resolutions ny=1, assuming wave propagates along the x-axis. The value of ymin and ymax is then not of importances since interpolation is only done in x and z direction.
    \item VTK files can be writted as long as at least nx or ny > 1. (i.e. 3D or 2D).
    \item The LSgrid functions are parallelized using openMP, hence a a significant performance boost is gain by running on multiple cores.
\end{itemize}

\subsection{[lsgrid2vtk]}
The primary objective of the library is to provide kinematics by calling the C extern functions provided in CFDwavemaker.h. It is also possible to make CFDwavemaker dump kinematics directly to file. This can be convenient for QA, or if wave kinematics is needed for other purposes.
When using grid interpolation ([lsgrid]), wave kinematics is stored on a sigma-stretched grid for quick interpolation. This grid can be dumped to VTK structured-grid files (.vts), a well established format provided through the VTK library. Since the lsgrid is logically structured (nx x ny x nl), the .vts format stores the geometry without connectivity tables. The files may be visualized and processed further using Paraview or other software. To achieve this, the tag [lsgrid2vtk] needs to be specified. Everytime the grid is updated, a new .vts file is written for the time t = t0.
